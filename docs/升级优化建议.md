# 升级优化建议

> 基于当前代码与运行状态（2026-11-15，v4 出厂配置，Rust/TS 合计约 11.4k 行，45 个后端测试）整理。
> 成本单位为**人日**，按"单人 + AI 辅助"估算，不含联调等待。

---

## 0. 评估基线

**已经做得不错的地方**（不建议再动）：

- 数据层：文件为权威源 + SQLite 镜像、幂等 schema、旁挂表、sha256 冲突协议——这套结构很稳，后续功能都能不下沉到迁移。
- 输出契约的容错：七层解析 + 人工修正，是小模型场景里最有价值的投资。
- 出厂配置版本化 + 三方比对，升级不会碾掉用户手改。

**当前最薄的三处**（后面的建议都围绕它）：

| 薄弱点 | 表现 |
|---|---|
| 长剧本的规模 | 回合数一多，读一次剧本要把全部正文 + 全部 prompt 快照搬进前端；每回合还重写整份 story.md |
| 单机数据安全 | 只有 `novel.db` 一份，没有自动备份；误删剧本/读错档不可恢复 |
| 断点韧性 | 生成失败/中断即丢弃整回合，没有"续写半段"的能力；`engines.retries` 从未被读取 |

## 2. P0：不做会越来越疼

### P0-1 回合按需加载 + 阅读器窗口化

**现状**：`commands.rs::list_passages` 一次 `SELECT` 出全部回合，含 `raw_output` 与 `bundle_snapshot`（整段 prompt，单条约 10–30 KB）。`choices_for` 又是每回合一次查询（N+1）。前端 `Reader.tsx` 把全部回合一次性渲染进 DOM，每回合重新拉一遍。

**量化**：200 回合时单次 `list_passages` 约 3–6 MB JSON、201 次 SQL；每次生成完都会走一遍。120 回合左右开始能感觉到卡顿，300 回合会明显掉帧。

**做法**：

1. `list_passages(story_id, offset, limit)` 分页，只取最近 N 段 + 一个总数；`bundle_snapshot` / `raw_output` 不进列表（新增 `get_turn_detail(turn_id)` 按需取，正是"上下文"抽屉要用的）。
2. choices 用一条 `WHERE passage_id IN (...)` 批量取，去掉 N+1。
3. 阅读器只渲染可视区前后各 2 屏（简单 windowing，不必上虚拟列表库），上方"加载更早"按钮。

**价值**：这是唯一一个"用得越久越用不了"的问题。
**收益**：200 回合首屏 < 200 ms，内存从数十 MB 降到个位数；顺带让"上下文抽屉"变成按需、不拖慢阅读。
**成本**：1.5 人日。**风险**：分页后"从这里重开 / 滚动记忆"要重新对齐，需回归一遍。

### P0-2 story.md 增量追加

**现状**：`finish_apply` 每回合把整本正文重新拼一遍再写盘（`SELECT` 全部回合 → 拼字符串 → `fs::write`）。**每回合 O(n) 读 + O(n) 写**，一部 300 回合的书累计写 ≈ 45 万回合文本。

**做法**：追加写（`OpenOptions::append`）+ 只在"重开/读档/导出"时才整篇重建；或干脆取消这层镜像，导出时现生成。
**收益**：每回合省一次全量 IO，SSD 上也能省 10–50 ms，且避免"写到一半崩溃导致镜像比库旧"。
**成本**：0.5 人日。

### P0-3 生成失败可续写 + 真重试

**现状**：`engine::stream_chat` 失败 → `discard_turn` 整回合丢弃（这是对的，半段不该入库），但**用户半小时的等待也一起丢了**。`EngineProfile.retries` 全项目无人读取。

**做法**：

1. 流式期间把已收到的正文定期写进 `passages.content_md`（`parse_status='streaming'`），失败后保留，阅读器给「**接着上次写**」按钮：把已写正文塞进 prompt 的"最近正文末尾"，要求接着写而不是重来。
2. `retries` 真正生效：连接错误/5xx 指数退避重试，4xx 不重试；重试时把已收到的 token 数作为 `max_tokens` 剩余量。
3. 失败原因分级：网络 / 超窗 / 鉴权 / 模型拒答，各给一句可操作的建议（比如超窗直接建议下调 `context_window`）。

**价值**：本地 30 tok/s 下一段要几分钟，失败重来最伤耐心。
**收益**：可感知的"不再白等"；顺带把 `retries` 从死配置变成真能力。
**成本**：1 人日。**风险**：续写可能重复上一句，需要 prompt 里明确"不要重复上段结尾"。

### P0-4 数据库自动备份 + 一键导入导出

**现状**：只有"恢复出厂配置"会备份 `config/`；`novel.db` 没有任何自动备份。当前重开某回合、读档都是**不可逆**操作（虽有快照表，但表在同一个库里——库坏了全没）。

**做法**：

1. 启动时 / 每 10 回合做一次 SQLite 在线备份（`rusqlite::backup`，已有依赖）到 `data/backups/db-YYYYMMDD-HHMM.db`，保留最近 10 份 + 每日一份。
2. 「导出世界观/剧本」→ 一个 zip（db 子集 + `worlds/<id>/**` + 相关 prompt），「导入」还原成新 id。
3. 关于页列出现有备份，一键还原（还原前先备份当前库）。

**价值**：这是单机应用，库里是几百小时的作品，且没有任何云端副本。
**收益**：误操作/磁盘故障可恢复；换机迁移从"整目录拷贝"变成"一个 zip"。
**成本**：0.5–1 人日（zip 可先用 `zip` crate 或直接目录拷贝）。

### P0-5 估算器校准 + 超限硬截断

**现状**：token 估算一律"中文 1 字 ≈ 1 token × 1.15"。对 qwen 系大致可用，但**对英文/代码/数字偏差明显**，且 `context_window` 只是"相信用户填的数字"。一旦超出，本地 llama.cpp 会直接报错或静默截断（截断通常发生在**最前面**，也就是人设和事件背景先没）。

**做法**：

1. 若引擎暴露 `/tokenize`（llama.cpp server 有）或能取到模型 tokenizer，就用真实计数；取不到则退化为现在的估算，但把系数写进 `engines.yaml` 可调。
2. 组包后若 `est > cap`，**按模块优先级硬截**（先砍最旧正文 → 摘要 → 目录 → 检索），保证"永不超窗"，而不是只给一条警告。
3. 预算面板直接显示"距上限还差 X tokens"，超了标红。

**价值**：现在最坏情况是"写着写着整个预设被吃掉了，模型开始胡说"。
**收益**：超窗类故障归零；预算面板从"参考"变成"承诺"。
**成本**：1 人日。**风险**：硬截可能砍掉用户以为在的设定——所以要先在面板里高亮"被截掉了哪些"。

## 3. P1：体验与功能补全

### P1-1 原生文件对话框

**现状**：导入设定集、导出小说都要**手打绝对路径**（因为早期为了绕开 Tauri dialog 在主线程死锁，把插件整个删了）。

**做法**：引回 `tauri-plugin-dialog`，只用它的**异步** API（`save()` / `pick_file()` 返回 Promise，`blocking_*` 一律禁用——就是当年踩的那个坑）。首次启动的迁移提示继续用 `MessageBoxW`，别碰。
**收益**：导出/导入从"要会找路径"变成点两下；错误率（路径写错）归零。
**成本**：0.5 人日。

### P1-2 章节 / 目录 / 阅读进度

**现状**：只有"回合"这一个粒度；300 回合的书没法跳转，只能滚。

**做法**：按"字数阈值 + 场景切换（◇ 分镜 / 地点变化）"自动切卷章，允许手动改章节名；阅读页加目录抽屉（章名 + 首句 + 字数），导出复用同一套章节数据。
**收益**：长书从"能读"变"好读"；导出的小说自带目录。
**成本**：1.5 人日（切章逻辑 0.5，抽屉与跳转 0.5，导出复用 0.5）。

### P1-3 全文搜索

**现状**：想找"之前写过的那段"只能靠翻。检索基础设施（FTS5 + 自研分词）已经现成。

**做法**：把 `passages.content_md` 也建一份 FTS（复用 `retrieval::tokenize`），搜索面板同时搜回合与设定卡，结果跳转到对应回合并高亮。
**收益**：复用已有分词，一天能落地；复习伏笔时很实用。
**成本**：1 人日。

### P1-4 状态卡可视化编辑 + 撤销

**现状**：档案抽屉只能看；`state.md` 要手改 JSON；`state_card_history` 有历史但**没有任何 UI**。

**做法**：抽屉里把 world/player 字段做成可编辑表单（`items`/`abilities` 用列表编辑器），每次人工修改落一条 history；加"撤销上一步"，以及"分析写错了"的纠正入口（改完提示"下一回合起生效"）。
**收益**：AI 记错（把"失去的魂骨"记成还在）能当场纠正，不用手改文件。
**成本**：1 人日。

### P1-5 导出增强

**现状**：只能导 Markdown。

**做法**：EPUB（`epub-builder` 或手写 zip + XHTML）、docx（复用 `docx` 技能思路或 `docx-rs`）；支持按卷导出、封面图、目录、作者/简介元数据。
**收益**：能直接给朋友看/发平台。
**成本**：1.5 人日（EPUB 1，docx 0.5）。

### P1-6 快捷键

`空格/→` 继续阅读、`1/2/3` 选选项、`Esc` 停止、`Ctrl+Z` 撤销上一步、`Ctrl+Enter` 提交自由输入。
**收益**：读小说时手不用离开键盘，体感提升明显。
**成本**：0.5 人日。

## 4. P2：代码可维护性

### P2-1 拆 `commands.rs`（1305 行）/ `context.rs`（1213 行）

**做法**：按职责分文件——`commands/` 下 `world.rs` `story.rs` `turn.rs` `config.rs`；`context/` 下 `bundle.rs` `modules.rs` `lore_inject.rs` `budget.rs`。抽一个 `TurnPipeline`（build → call → parse → apply），让"自动连写""重试""续写"这些横切逻辑有地方挂。
**收益**：新增一种生成模式（比如"多人对话生成"）时不用再改 1300 行的文件；review diff 也小。
**成本**：1.5 人日（纯搬运 + 编译通过 + 回归测试）。

### P2-2 阅读页 hook 化

**现状**：`Reader.tsx` 616 行、十几个 `useState` + 若干 `useRef`，生成状态机（draft / earlyDeltas / appliedTurns / autoLeft / resume）散在组件里，已经出现过"监听器泄漏导致重复应用"这类竞态。
**做法**：抽 `useGeneration()`（事件订阅、去重、自动连写循环）与 `useStoryData()`（reload、分页、乐观更新），组件只负责渲染。
**收益**：竞态只在一个地方处理；后续加"重新生成这一段""对比两个版本"不会长出第四套状态。
**成本**：1 人日。

### P2-3 配置清理

**现状**：4 个"看着能调其实没人读"的项：`app.yaml` 的 `lore_chunk_threshold` / `lore_char_threshold`，`policies` 的 `estimator.strategy` / `retrieval.fusion`。
**做法**：要么实现（`fusion` 支持 weighted），要么删掉；再加一层"未知键警告"（serde 解析后对比已知键集合，启动时写进 `needs_merge` 那种提示）。
**收益**：配置面板的每一项都可信；用户改错了能被告知。
**成本**：0.5 人日。

### P2-4 结构化日志 + 诊断包

**做法**：`tracing` + 按天滚动写 `data/logs/`（记录：模式、模型、prompt tokens、耗时、首 token 延迟、解析告警、检索命中）；「关于」页一个"导出诊断包"（日志尾部 + 配置脱敏 + schema 版本 + 最近 3 个 prompt）。
**收益**：出问题能定位到"是模型/网络/解析/预算"哪一层，而不是靠复述现象。
**成本**：1 人日。

### P2-5 CI / clippy / pre-commit

`cargo clippy -D warnings` + `tsc --noEmit` + `cargo test`，本地 pre-commit 或 GitHub Actions。
**收益**：现在靠我手动跑，容易漏；自动化后不会带警告进主干。
**成本**：0.5 人日。

### P2-6 集成测试补强

给 `build_bundle`（固定 fixture 库 → 断言关键模块顺序与 token 数区间）、`apply_output`（完整四段 → 断言状态卡/摘要/角色变化）、`restore_save`、`export_novel` 各写金文件快照测试。
**收益**：P2-1/P2-2 这类重构才有护栏；现在 45 个测试偏单元层。
**成本**：1 人日。

## 5. P3：探索项（有闲再做）

### P3-1 向量增量维护 + 内置 embedding

现状：新增/修改设定卡后不会自动补向量，得手动点"建立索引"；且依赖 LM Studio 里恰好加载了 embedding 模型。
做法：`reslice` 后标记脏、后台线程增量补；或用 `fastembed-rs` 内置一个小模型（~80 MB），零外部依赖。
**收益**：向量检索从"要我记得点"变成"一直有效"。
**成本**：2 人日。

### P3-2 分支存档（fork）

现状：读档是**覆盖式**——回到第 5 回合，第 6 回合之后的文本就没了。
做法：读档时可选"另开一条线"，`stories` 复制一份，两条线共享世界观与设定集，阅读页能切换/对比。
**收益**：真正实现"我后悔上一步的选择"而不销毁原线；也方便 A/B 两种走向。
**成本**：2.5 人日（数据模型已是旁挂表，主要是 UI 与列表组织）。

### P3-3 分层摘要

现状：滚动摘要靠"追加 + 超预算裁头"，200 回合后早期剧情会被裁掉（等于失忆）。
做法：每 10 回合生成"章摘要"，每 10 章生成"卷摘要"，注入时用"近 3 章摘要 + 卷摘要 + 当前摘要"。
**收益**：长线不失忆，且比现在更省 token。
**成本**：1.5 人日。

### P3-4 听书（TTS）

**做法**：系统 SAPI（Windows 自带，零依赖）朗读正文，逐段高亮，支持"读到选项处停"。
**收益**：通勤/躺着也能追更。
**成本**：1.5 人日。

## 6. 如果只做三件事

1. **P0-1 + P0-2（1.5 + 0.5 人日）**：先把"越写越卡"这个天花板抬掉，否则写长了就得换应用。
2. **P0-4（0.5 人日）**：给不可再生的数据一条退路，投入产出比最高。
3. **P0-3（1 人日）**：本地模式一段几分钟，失败不重来是体感提升最大的一项。

两周节奏建议：**第 1 周** P0-1/2/4 + P1-1；**第 2 周** P0-3/5 + P1-2，其余按兴趣插空。
